# 배포를 고려한 디코더·인코더 비교

조사일: 2026-11-13

## 범위와 판단 기준

VS Code 확장 기능을 사용자에게 배포하는 상황을 기준으로 소프트웨어 재배포 조건, 지원 코덱, 편집 용도와 통합 비용을 비교한다. 프로젝트 라이선스, 상업적 배포 여부, 배포 지역과 대상 플랫폼은 아직 정해지지 않았다. 따라서 아래의 **조건부 가능**은 해당 구성과 의무를 충족할 때의 후보라는 뜻이며, 실제 배포 승인을 뜻하지 않는다.

코덱 표준(H.264 등), 그 구현체(x264 등), 컨테이너(MP4 등)는 서로 다르다. 소프트웨어 저작권 라이선스에서 재배포가 허용되어도 코덱 특허 조건이 자동으로 해결되는 것은 아니다. 반대로 GPL도 의무를 준수할 수 있다면 배포 가능한 라이선스다. 특허 라이선스의 범위와 비용은 제품·지역·용도에 따라 별도 확인한다.

## 현재 제품 범위

사용자는 다양한 압축 형식보다 배포 가능한 오픈 라이선스 구현체를 요구했다. 따라서 MP4/H.264/AAC는 필수 MVP 목표가 아니다. 아래 MP4 관련 분석은 선택지를 비교하기 위한 참고 자료이며, 실제 채택은 필요성이 확인될 때 별도로 결정한다. 초기 출력은 WebM/VP9/Opus 조합을 우선 검증하되 특허 허여 조건, 재생 호환성과 실제 빌드를 확인한 후 확정한다.

## 결론과 권장 후보

- **처리 기반 1순위:** 사용자가 별도 설치한 FFmpeg를 기본 후보로 삼는다. 직접 동봉이 필요한 경우 **LGPL 구성의 FFmpeg**를 별도로 검토한다. 컨테이너 처리, 탐색, 디코딩, 오디오 처리와 렌더링을 한 엔진으로 구성하기 쉽다. 검증에 사용한 바이너리의 빌드 옵션과 의존성을 기록하고, 직접 배포하는 경우 해당 라이선스 의무를 이행해야 한다.
- **입력 디코딩:** WebM/VP9/Opus를 우선 검증한다. H.264·AAC 등 추가 입력은 필요성과 특허 조건을 별도 확인한 후 검토한다.
- **참고: MP4/H.264/AAC 출력:** FFmpeg의 내장 AAC 인코더와 H.264 인코더 후보를 조합한다. H.264 인코더와 특허 처리는 **미결정**이다. FFmpeg의 LGPL 구성만으로 H.264 소프트웨어 인코더가 자동 제공된다고 가정하지 않는다.
- **우선 검증할 출력:** 배포 조건을 비교하기 위한 WebM/VP9/Opus 후보는 FFmpeg + libvpx + libopus다. 성능과 재생 호환성을 검증해야 한다.
- **GPL을 수용하는 경우:** x264를 포함한 FFmpeg 빌드도 조건부 후보다. 프로젝트의 배포 모델과 GPL 의무를 먼저 검토한다.

각 라이브러리 자체의 라이선스와 이를 포함한 **전체 FFmpeg 빌드**의 라이선스는 각각 확인해야 한다. 컨테이너 처리, 오디오 믹싱, 정확한 탐색은 개별 코덱 라이브러리만으로 완성되지 않는다.

## H.264 선택 시 세부 비교

### FFmpeg 내장 H.264 디코더

FFmpeg의 내장 H.264 디코더는 해당 입력을 추가할 때 검토할 후보다. [FFmpeg 문서](https://ffmpeg.org/general.html#OpenH264)는 OpenH264 디코더가 내장 디코더보다 제한적이며 B프레임과 일부 Main/High 프로파일 기능을 지원하지 않는다고 설명한다. 실제 지원 프로파일과 정확한 탐색은 선정한 버전과 테스트 파일로 검증한다. 소프트웨어 배포 조건 외에 H.264 특허 검토가 필요하다.

### OpenH264 인코더

OpenH264의 소스는 BSD-2-Clause로 배포 가능하지만, [Cisco FAQ](https://www.openh264.org/faq.html)와 [바이너리 라이선스](https://www.openh264.org/BINARY_LICENSE.txt)에 따르면 Cisco가 제공하는 특허 풀 관련 혜택에는 Cisco 제공 바이너리를 최종 사용자 기기에 **별도 다운로드**하는 등의 조건이 있다. 사용자가 활성화·비활성화할 수 있어야 하는 등 다른 조건도 원문에서 확인해야 한다. 자체 컴파일하거나 VSIX에 묶어 배포하면 그 혜택을 당연히 적용할 수 없다. Cisco의 안내는 다른 특허권자의 청구까지 보증하지 않는다.

FFmpeg 연동에는 `--enable-libopenh264`가 필요하다. 플랫폼별 Cisco 바이너리 제공 여부, 다운로드·무결성 검증, 오프라인 설치, 프로파일과 화질·속도는 구현 전 검증한다. Cisco 다운로드 방식은 함께 번들하는 방식과 구분하여 검토한다.

### x264 인코더

[x264 공식 안내](https://images.videolan.org/developers/x264.html)에 따르면 GPL과 별도 상용 라이선스 선택지가 있다. GPL을 수용하는 배포 구성이라면 비교할 수 있지만, 프로젝트의 라이선스가 미정이므로 기본 채택을 확정하지 않는다. 상용 라이선스의 범위와 비용 및 H.264 특허 조건도 별도 확인한다. GPL이 상업적 배포 자체를 금지하는 것은 아니다.

### 운영체제·하드웨어 인코더

FFmpeg는 플랫폼 인코더 연동도 제공한다. 예를 들어 [FFmpeg 코덱 문서](https://ffmpeg.org/ffmpeg-codecs.html)는 Media Foundation 인코더를 설명한다. 이 경로는 설치된 OS, 드라이버, 하드웨어와 API의 지원에 의존하므로 모든 사용자에게 동일한 기능을 보장하지 않는다. 플랫폼별 재배포·이용 및 특허 조건을 확인하고, 미지원 시 사용할 대체 경로를 마련해야 한다.

## 오디오와 대안 출력

- **AAC:** [FFmpeg 내장 AAC 인코더](https://ffmpeg.org/ffmpeg-codecs.html#Native-FFmpeg-AAC-Encoder)는 LGPL 구성 후보이지만 AAC 관련 특허 검토는 별개다. FDK-AAC는 FFmpeg와 GPL을 함께 사용하는 구성에서 `--enable-nonfree`가 필요한 것으로 [FFmpeg가 설명](https://ffmpeg.org/ffmpeg-codecs.html)하므로 해당 빌드는 배포 후보에서 제외한다. 다른 구성의 조건을 일반화하지 않고 별도 검토한다.
- **VP9 + Opus:** libvpx와 libopus는 각각의 고지와 특허 허여 조건을 확인해 FFmpeg에 포함하는 후보이다. [libvpx 라이선스](https://github.com/webmproject/libvpx/blob/main/LICENSE), [libopus 라이선스 안내](https://github.com/xiph/opus-website/blob/master/license.md)를 참고한다.
- **AV1:** libaom은 [소프트웨어 라이선스](https://aomedia.googlesource.com/aom/+/refs/heads/main/LICENSE)와 별도의 [특허 라이선스](https://aomedia.googlesource.com/aom/+/refs/heads/main/PATENTS)를 제공한다. 특허 허여의 범위와 조건이 모든 제3자 청구에 대한 보증은 아니다.

## 배포 전 확인 및 검증

1. 프로젝트 라이선스, 배포 국가·대상, 상업적 사용과 VSIX 동봉 또는 별도 다운로드 방식을 결정한다.
2. 플랫폼별 바이너리의 출처·버전·해시, FFmpeg `configure` 옵션, 포함 라이브러리와 해당 라이선스를 기록한다. `ffmpeg -version`, `-buildconf`, `-decoders`, `-encoders`로 실제 빌드를 확인한다.
3. LGPL 구성이라면 적용 라이선스 전문, 저작권 고지, 정확히 대응하는 소스 및 수정분과 빌드 방법, 라이브러리 교체·재링크 등 배포 방식에 적용되는 의무를 검토하고 이행한다. [FFmpeg의 LGPL 체크리스트](https://ffmpeg.org/legal.html)를 참고한다.
4. OpenH264를 Cisco 바이너리 방식으로 사용할 경우 원문 조건과 플랫폼별 배포 경로를 확인한다. 자체 번들·자체 빌드는 별도로 평가한다.
5. H.264/AAC 등 각 코덱과 대상 지역에 관한 특허·계약 조건 및 비용을 확인한다. 소프트웨어 라이선스의 재배포 허용만으로 이를 완료했다고 보지 않는다.
6. 대표 입력 파일에서 프레임 정확도, VFR, 오디오 동기화, 출력 호환성, 성능과 플랫폼별 동작을 검증한다. 검증 전까지 후보 선정은 잠정적이다.
7. 릴리스에 제3자 고지와 필요한 소스 제공 경로를 포함하고, 실제 패키지에 포함된 바이너리와 기록이 일치하는지 확인한다.
